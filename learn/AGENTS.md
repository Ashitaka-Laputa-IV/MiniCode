# learn/ 写作简报

这份文件写给在 `learn` 分支上写文档的 agent。目标只有一个：让读者重新获得**改动这个项目的能力**，而不是读完一份关于项目的资料。

## 读者

- 写过或长期维护过 MiniCode，隔了几个月回来；
- 会 Python、pytest，知道 LangGraph 的基本概念，不需要补课；
- 下一次动作是改代码或审 PR，不是面试，也不是技术选型；
- 愿意投入 60–90 分钟。

所以：不要解释 `uv sync`，不要复述 README / 根目录 AGENTS.md，不要教框架基础。读者的时间只花在**从代码里看不出来的东西**上。

## 合格标准

读完后，读者应该能对任意一个新场景回答三件事：

1. **预测**：输入这样一条命令，系统会怎么走、在哪里停、输出到哪里；
2. **定位**：想改这个行为，应该动哪个函数、哪条分支；
3. **判断**：这个改动会不会破坏既有约束，代价是什么。

任何一篇文档，如果删掉后这三种能力不变，它就不该存在。

## 唯一主线

所有文档围绕同一个真实场景展开：

`uv run minicode "fix the failing test"`

路径是：`cli.main()` → `build_agent()` → Deep Agents 图 → 模型发出 tool_call → `Policy` / HITL → `PolicyShellBackend` 执行 → stdout/stderr。

规则：

- 不另造玩具例子。需要举例时，把主线推进一格。
- 概念在主线走到它时再引入，不提前定义，不集中罗列。
- 读者每读完一节，都应该知道"现在控制权在谁手里、状态存在哪里"。

## 写法

- 中文，第二人称，散文为主；代码标识符保持原样。
- 每节第一句给判断，再给机制，再给证据。不要从"背景"开始铺垫。
- 抽象一句，具体一句。任何机制说明后面必须跟本仓库的实例。
- 开头不写"本文将……"，直接给这篇要解决的问题和结论。
- 一段一个意思，超过 5 行就拆。
- 表格只用于对比，不超过全文 1/3；清单只在真的并列时用。
- 单篇 120–220 行，README 60–100 行。超了通常是在抄代码或补覆盖面。
- 不用"首先/其次/最后"，不用"值得注意的是"，不用"优雅/强大/完善/健壮"。
- 不写"小结"复读前文。要收尾就给一条可执行的判断规则。

## 证据

- 代码是唯一事实来源；README 和根目录 AGENTS.md 可能过期，冲突时以代码和测试为准。
- 每个"为什么"必须有证据：代码结构、测试断言、提交信息、PR 讨论、配置默认值。找不到证据就写"没有记录"，不要补一个合理故事。
- 测试是决策的化石：断言了什么、mock 了什么、故意不测什么，往往比注释更能说明约束。
- 不确定的行为，跑一遍或写个最小脚本验证，再写。

## 代码链接

- 链到"做决定的那一行"：函数定义、条件分支、赋值、默认值。不链 import 和空行。
- 单行锚点，例如 [`build_agent()`](../src/minicode/agent.py#L132)；不要写区间。
- 链接文字说明那里发生了什么，不要写"这里""源码"。
- 正文同时写出符号名。行号会漂移，符号名不会。
- 写完在当前 HEAD 逐个打开验证。

## 两个对照

**资料 vs 教学（机制）**

> 资料：MiniCode 提供 read-only、ask、yolo 三种权限模式。
>
> 教学：三种模式的差别不是"松紧"，而是"谁做决定"：read-only 由 `Policy` 直接拒绝，ask 把决定推给人，yolo 跳过人但跳不过 hard deny。所以 yolo 的风险不在那几条硬禁区，而在文件系统。

**资料 vs 教学（状态）**

> 资料：单次任务使用 `InMemorySaver`，REPL 使用 `SqliteSaver`。
>
> 教学：单次任务也要 checkpointer，因为 ask 模式的 interrupt/resume 依赖它；区别只是这个状态要不要活过进程。`--thread` / `--db` 只对 REPL 有意义，就是因为只有它的状态留下来了。

## 过程

1. 先读：`git log --oneline -20`、相关 PR、`src/`、`tests/`。被反复修改的地方、测试里别扭的断言、只在一处生效的默认值，通常就是教学点。
2. 列 5 行提纲：读者变化、3 个必须回答的问题、用到的代码入口、计划删掉的内容。
3. 写一篇，验证一篇。不要一次生成六篇；一次生成必然同构。
4. 通过自检后再进下一篇。

顺序：`02` → `04` → `03` → `01` → `05` → `README`。主线和代码没定下来之前，介绍和审阅都会写成空话。

## 完成前自检

- [ ] 读者能按 `02` 复述主线，按 `04` 找到改动点，按 `05` 提出问题
- [ ] 每条命令都在当前 HEAD 跑过，或明确标注未验证
- [ ] 每个行号链接都打开确认过
- [ ] 每个"为什么"都有代码、测试、提交或 PR 证据
- [ ] 每个抽象结论后面都有本仓库的实例
- [ ] 删掉了所有"不读本仓库也能写"的段落
- [ ] 六篇没有重复展开同一事实
- [ ] 没有编造动机，没记录的地方就写"没有记录"
- [ ] `learn/` 之外没有改动

## 分支与版本

- `learn` 基于 `dev`。开始前：`git fetch origin && git switch learn && git merge origin/dev`。
- 只改 `learn/`。`src/`、`tests/`、配置、CI 一律不动；文档里发现的问题写进文档，不改代码。
- 文档描述合并后的 HEAD。在 `README.md` 记录 `git rev-parse --short HEAD` 和核对日期。
- 未合入 `dev` 的 PR、分支、设计只能标为"计划中"，不得写成现状。
- 代码或行为变了，就更新对应篇目并重验所有链接；不要留下"上次是对的"。

## 不确定时

- 宁可少写一个决策，也不要编一个动机。
- 宁可删掉一节，也不要为了对称补一节。
- 拿不准读者是否需要某段：默认删。
- 范围、篇目、深度需要用户决定时直接问，不要自行扩大。

无需将`learn`合并到`dev`.
